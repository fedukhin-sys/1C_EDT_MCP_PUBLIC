# Список MCP-инструментов EDT_MCP

Справочник ведётся вручную по коду (`*Tool.java`, методы `name()` / `description()`)
и регистрации в `plugin.xml` каждого бандла. Генератора нет — при добавлении инструмента
файл нужно править руками.

Сверить фактическое число можно так:

```bash
grep -c "<tool " bundles/*/plugin.xml
```

Всего реализовано **107 инструментов** в **12 tool-бандлах**
(всего бандлов в сборке 14: 12 tool-бандлов + `core` + `ui`).

|---|---|---|
| `tools.edt` | Workspace и проекты | 10 |

## Информационные базы и развёртывание (`tools.infobase`, 10)

| Инструмент | Описание |
|---|---|
| `list_infobases` | Список информационных баз, зарегистрированных в 1C:EDT (с фильтром по папке/типу). |
| `get_infobase` | Детали информационной базы по имени или uuid. |
| `get_infobase_sync_state` | Диагностика окна «Обновление приложения: Конфигурация информационной базы … не синхронизирована с проектом …» при запуске клиента из EDT. Только чтение: ничего не пишет ни на диск, ни в настройки EDT; монитор состояния синхронизации EDT держит только на время копии снимка. По проекту конфигурации и **каждому** его проекту расширения: `equalityState` (`getEqualityState`: `EQUAL` / `NOT_EQUAL` / `LOADING`), `connected`, `projectDirty` (EDT 2026.1+), `updateState` проекта. `applicationUpdateState` — ответ самой EDT при запуске (`IApplicationManager.getUpdateState`: `UPDATED` — окна нет; `INCREMENTAL_UPDATE_REQUIRED` / `FULL_UPDATE_REQUIRED` / `UNKNOWN` — окно; `BEING_UPDATED` — запуск отменяется), `computedUpdateState` — то же правило по строкам проектов, `launchDialogExpected` и `summary` с виновными проектами. `details: true` — расходящиеся файлы по проектам: подписи (SHA-256) против снимка синхронизации в памяти EDT (с ним она сравнивает сейчас) и на диске (`index.idx` — его EDT загрузит после перезапуска; совпадает с памятью — `sameAsMemory: true`); `maxFiles` (50) — предел каждого списка. Проект расширения в аргументе — проверяется его конфигурация; база по умолчанию — связанная с конфигурацией. Явная несвязанная база — с предупреждением: приложения EDT для такой пары нет, поэтому `applicationUpdateState` и `launchDialogExpected` — `null`, а правило — только справочно. Чего нет в этой версии EDT — `null` с причиной. |
| `create_infobase` | Создать файловую ИБ через `1cv8.exe` и зарегистрировать её в 1C:EDT. |
| `associate_infobase` | Связать проект с информационной базой (опционально как основную). Для проекта конфигурации: 1C:EDT 2026.1 связывает базу с одним проектом, а проект расширения следует за базой родительской конфигурации — связать его откажет «already associated with project …». |
| `deploy_project` | Обновить конфигурацию ИБ из проекта (синхронизация проект → ИБ). Запрошенная база сверяется с ассоциацией проекта: если проект связан с другими базами, операция отменяется — обойти можно аргументом `allowForeignInfobase: true`. Если ассоциации нет, деплой идёт с предупреждением. |
| `create_infobase_from_dt` | Сценарий «новый проект»: создаёт файловую или серверную базу (кластер 1С + БД в СУБД, регламентные задания по умолчанию заблокированы), загружает в неё `.dt`, связывает проект и обновляет его из базы. Для SERVER `dbName` (по умолчанию = `ref`) — только **новая** БД, и это защищено: если БД с таким именем в СУБД уже есть (1С подключает к ней новую базу), задание останавливается сразу после создания, до загрузки `.dt`, в EDT база не регистрируется; регистрацию в кластере удалить без `--drop-database` и повторить с новым `dbName`. `.dt` — выгрузка базы с реальной конфигурацией. Фоновое задание. |
| `update_extensions_from_cfe` | Загружает `.cfe` в связанную базу (расширение создаётся или заменяется и применяется; загрузка — пакетным конфигуратором с `-Extension`), затем обновляет проекты расширений из базы. Имя расширения — из имени файла или `name`: это имя, под которым расширение загружается в базу, и оно должно совпадать с собственным именем расширения внутри `.cfe` — иначе применение может упасть «Расширение с таким именем уже существует!», а загруженное, но не применённое расширение останется в конфигурации базы (результат подскажет, что делать). Расширения обрабатываются независимо. Проекты расширений с базой не связываются — они следуют за базой родительской конфигурации; связанный только с другой базой проект не обновляется (`WARNING`). Нет проекта — подсказка: создать пустой проект расширения и выполнить для него `update_project_from_infobase` с `discardProjectChanges: true`. Перед обновлением каждого проекта инструмент закрывает сеанс агента конфигуратора EDT на базе и сбрасывает быструю проверку EDT «база не менялась» (иначе EDT могла бы ответить «изменений нет», не сравнив загруженное с проектом); не вышло — ответ «изменений нет» приходит с предупреждением. `discardProjectChanges: true` — полная замена их содержимого. Фоновое задание. |
| `restore_infobase_from_dt` | Загружает `.dt` в связанную базу — **все данные базы заменяются** — и обновляет из неё проект конфигурации и его проекты расширений (без своей связи с базой или связанные с этой; прочие перечисляются в `extensionProjectsOfOtherInfobases`). `backupTo` — сначала выгрузить текущую базу. Перед обновлением каждого проекта инструмент закрывает сеанс агента конфигуратора EDT на базе и сбрасывает быструю проверку EDT «база не менялась» (иначе EDT могла бы ответить «изменений нет», не сравнив загруженную базу с проектом); не вышло — ответ «изменений нет» приходит с предупреждением. `discardProjectChanges: true` — полная замена их содержимого. Фоновое задание. |
| `update_project_from_infobase` | «Проект ← база»: содержимое проекта (конфигурации или расширения) заменяется версией из связанной базы, удалённые в базе объекты удаляются и из проекта. Проект расширения без `infobase` берёт базу родительской конфигурации. Отказывает без `discardProjectChanges: true`, если в проекте есть правки, не залитые в базу, или у EDT нет состояния синхронизации проекта с базой (новый проект); без флага проект проверяется ещё раз прямо перед забором изменений базы. `discardProjectChanges: true` — **полная замена**: из базы выгружается вся конфигурация, файлы, которых в базе нет, удаляются из проекта. Новый или пустой проект — `discardProjectChanges: true`; `deploy_project` заменяет конфигурацию базы содержимым проекта, для пустого проекта его не вызывать. Только проекты конфигурации и расширений (проект внешних отчётов и обработок — отказ). Перед обновлением инструмент закрывает сеанс агента конфигуратора EDT на базе (после прошлого обновления EDT отвечает «изменений нет», не спрашивая базу, пока сеанс открыт) и сбрасывает её быструю проверку по идентификатору поколения данных (загрузка `.dt`/`.cfe` его не меняет) — тогда EDT сравнивает базу с записанным состоянием. Не вышло — ответ «изменений нет» приходит с предупреждением и причиной; с `discardProjectChanges: true` такой ответ — аномалия: результат говорит, что проект НЕ заменён, а записанное состояние синхронизации (отложенное для полной замены) возвращается на место. Фоновое задание. |

У всех четырёх заданий синхронизации (`create_infobase_from_dt`, `update_extensions_from_cfe`, `restore_infobase_from_dt`, `update_project_from_infobase`) первый шаг — `wait-edt-checks`: сразу после запуска EDT или открытия (создания) проекта EDT сама фоново проверяет состояние синхронизации проектов с базами, и задание ждёт окончания этих проверок **до 10 минут** (не дождалось — `FAILED` «…повторите позже; ничего не тронуто»). Без `discardProjectChanges` у `update_extensions_from_cfe` и `restore_infobase_from_dt` вторым шагом идёт `check-projects` — проверка проектов, которые задание перезапишет, до загрузки `.cfe`/`.dt`; её отказ советует сохранить правки отдельно (git; у `.dt` ещё `backupTo`) и повторить с `discardProjectChanges: true` — `deploy_project` здесь не поможет, загрузка заменит залитое. После загрузки любой отказ, сбой или предупреждение обновления проекта говорит: `deploy_project` сейчас не вызывать, базу забрать в проект `update_project_from_infobase` с `discardProjectChanges: true`. Перед закрытием сеанса агента, сбросом быстрой проверки и отметкой проекта задания ждут окончания чужой синхронизации базы (до 2 минут).

## Журнал регистрации (`tools.eventlog`, 2)

| Инструмент | Описание |
|---|---|
| `get_event_log_path` | Получить путь к каталогу `1Cv8Log` и список партиций для зарегистрированной в EDT ИБ (file и server). |
| `query_event_log` | Запрос событий журнала регистрации (`.lgf`/`.lgp`) с фильтрами: период, пользователь, приложение, событие, важность, сессия (`session`), подстрока в комментарии и метаданных; постраничность (`limit`, `offset`) и порядок (`order` = `date_asc` / `date_desc`). |

Оба инструмента требуют указать ИБ **одним из** взаимоисключающих способов
(`name` / `uuid` / `logDir`). В `inputSchema` это выражено через `anyOf`/`oneOf` и с 1.20.0
публикуется клиенту (record `JsonSchema` MCP SDK этих полей не несёт — они дописываются
при сериализации tools/list); требование продублировано и словами в `description`.

`query_event_log` возвращает ключ `partial` = `true`, если хвост активной `.lgp`
не дочитан (файл пишется прямо во время чтения).

## Запуск клиента 1С (`tools.client`, 5)

| Инструмент | Описание |
|---|---|
| `run_client` | Запустить тонкий или толстый клиент 1С для информационной базы. |
| `list_running_clients` | Список запущенных сеансов клиента 1С (с фильтром по ИБ/типу клиента). С `includeForeign: true` дополнительно показывает процессы платформы (`1cv8`, `dbgs`), поднятые другими инстанциями EDT или оставшиеся от прошлых сеансов — они помечены `foreign: true`, держат информационную базу (из-за чего `deploy_project` превращается в тихий no-op) и не гасятся через `stop_client`. |
| `stop_client` | Остановить сеанс клиента по `sessionId` (мягко → принудительно по таймауту). |
| `list_launch_configurations` | Список launch-конфигураций EDT типа «Клиент 1С:Предприятия»: имя, проект, ИБ, тип клиента, пользователь. Пароль не возвращается никогда — только признак `hasPassword`. |
| `run_launch_configuration` | Запустить launch-конфигурацию EDT (`mode` = `run`/`debug`) — тем же кодом, что кнопка запуска в IDE: учётные данные, тип клиента и версия платформы берутся из самой конфигурации. Предпочтительный способ запуска клиента, когда конфигурация в EDT уже настроена. |

## Редактирование метаданных (`tools.md`, 34)

| Инструмент | Описание |
|---|---|
| `list_md_objects` | Список объектов метаданных проекта (с фильтром по виду). Работает и на external-object проектах (файловый скан `src/`). |

С 1.20.0 создаются и `Task`/`BusinessProcess`/`ChartOf*`/`ExchangePlan`/`DocumentJournal`; не-creatable остались `CommonForm`/`CommonPicture` (нужны сопутствующие артефакты) — отбиваются с подсказкой использовать `borrow_md_object`. Донастройка: бизнес-процессу задай задачу (`set_md_property property=task`), журналу — регистрируемые документы (`add_register_recorder`). |

| `add_attribute` | Добавить реквизит/измерение/ресурс к объекту метаданных. |
| `rename_attribute` | Переименовать реквизит/измерение/ресурс объекта метаданных. |
| `set_md_type` | Задать тип реквизита/измерения/ресурса объекта метаданных через DOM. |
| `set_constant_type` | Задать тип значения константы (примитив, ссылка, составной тип). |
| `add_tabular_section` | Добавить табличную часть к объекту метаданных (Справочник/Документ/Бизнес-процесс/Задача/План...). |
| `add_tabular_section_attribute` | Добавить колонку (реквизит) к существующей табличной части. |
| `add_enum_value` | Добавить значение в перечисление (`Enum`). Существующие значения читаются через `list_attributes` / `get_md_object`. |
| `add_register_recorder` | Связать документ как регистратор регистра (накопления/бухгалтерии/расчёта/сведений). С 1.20.1 принимает и `DocumentJournal` — регистрирует документ в журнале (односторонняя связь `registeredDocuments`). |
| `add_subsystem_content` | Добавить ссылку на объект метаданных в состав подсистемы (привязка командного интерфейса). |
| `borrow_md_object` | Заимствовать объект метаданных из базовой конфигурации в расширение. |

## Запуск тестов xUnit (`tools.testrun`, 4)

| Инструмент | Описание |

## Обезличивание ПДн (`tools.privacy`, 4)

Управляющий контур слоя обезличивания (152-ФЗ). Само обезличивание работает автоматически —
на ответах инструментов, помеченных `IMcpTool.returnsInfobaseData()` (`get_variables`,
`evaluate`, `get_stack`, `query_event_log`, `run_tests`, `run_test_method`, `set_variable`,
`get_job_status` — тексты ошибок платформы и СУБД из фоновых заданий).

| Инструмент | Описание |

| `get_pii_catalog` | Текущий union-каталог ПДн открытых проектов. |
| `set_infobase_pii_flag` | Установить флаг `containsRealPersonalData` у инфобазы (снятие = объявить тестовую БД без ПДн, логируется). |
